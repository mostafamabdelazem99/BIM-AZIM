System Architecture

How it works

A layered design connecting AI to seven different BIM/CAD APIs across three languages (.NET, Ruby, Python), plus direct Office output — each wired the way its own API actually works.

BIM-AZIM MCP Server Node.js + TypeScript · tool registry · routes to the right engine bridge (plus Office tools, generated in-process)

New Integration

Why Tekla Structures connects differently

Revit and Navisworks only expose their APIs to code running inside their own process. Tekla's Open API is built to be called from the outside.

① No in-process add-in required

new Tekla.Structures.Model.Model() from any external .NET process connects straight to the running Tekla Structures session over Tekla's own remoting layer.

② Runs as its own service

The bridge can be started, stopped, and updated independently of Tekla itself — no reloading an add-in, no restarting Tekla to pick up a fix.

③ Same contract as the others

GET /health and POST /tools/:name — identical shape to the Revit and Navisworks bridges, so the MCP server treats all three uniformly.

How this maps to the tool

  • Unreal Engine — real native VR. A unreal_play_in_vr tool drops you straight into the live editor scene with a headset.
  • 3ds Max — real native glTF export. max_export_scene can write a .glb you can drop straight into this viewer or any WebXR/AR app.
  • Revit, Navisworks, AutoCAD, SketchUp — their public APIs don't expose a glTF/USDZ exporter directly (see docs/ARCHITECTURE.md). Export via FBX/OBJ/DWG today, convert with a tool like Blender, then drop the result in here.
